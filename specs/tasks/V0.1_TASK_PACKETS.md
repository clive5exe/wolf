# v0.1 Task Packets

Packets for **open** work (T-022 … T-030). Tasks T-001…T-021 were implemented
in the founding scaffold session. Their acceptance criteria live in the specs
they implement and their evidence is the test suite (`scripts/verify.sh`).
Every future task gets a packet in this format before a builder touches code.

## Packet template (copy for new tasks)

```
ID · Objective · Business reason · Architecture refs · Inputs → Outputs ·
Allowed paths · Forbidden paths · Acceptance criteria · Non-goals ·
Tests required · Safety class (S0/S1/S2) · Rollback · Completion evidence
```

## T-022. Policy onboarding flow (NL → draft → confirm → active)

- **Objective:** TUI onboarding screen + `PolicyService.draft_from_text()`
  using the provider to fill `PolicyDraft`, then a field-by-field confirm
  form that activates policy v1.
- **Business reason:** PRODUCT.md J2. The "financial advisor, not chatbot"
  first impression.
- **Architecture refs:** INVESTMENT_POLICY_SPEC §2, 3. PROVIDER_SPEC §5. ADR-0011.
- **Inputs → Outputs:** goals text → `PolicyDraft` (provider) → confirmed
  `InvestmentPolicy` v1 + `policy.created` event + notification.
- **Allowed paths:** `src/tradeos/tui/screens/onboarding.py`,
  `src/tradeos/runtime/policy_service.py` (extend), `src/tradeos/providers/prompts.py`
  (add draft prompt), `tests/unit/test_policy_onboarding.py`, `tests/integration/`.
- **Forbidden paths:** `risk/`, `execution/`, `brokers/`, provider adapter internals.
- **Acceptance criteria:** ⚡ fields require explicit confirmation. Provenance
  (`user_stated/model_inferred/default`) rendered per field. Provider-down
  path falls back to blank form. Draft with `autopilot` set is rejected with
  visible message. Round-trip test from PRODUCT.md J2 example passes.
- **Non-goals:** editing flows post-activation (separate task), multi-policy.
- **Tests:** unit (draft validation, provenance mapping), Pilot TUI test
  (confirm flow), integration (event emitted, reload identical).
- **Safety class:** S1. **Rollback:** revert commit. No schema/migration changes allowed.
- **Evidence:** verify.sh green + Pilot screenshot in PR + event-log excerpt.

## T-031. TUI visual system + boot & den screens ☑ done 2026-08-05

- **Objective:** replace the plain dashboard with the approved terminal
  direction: palette and motion tokens, pure glyph renderers (drift gauge,
  sparkline, freshness), the boot check cascade, and the den dashboard.
- **Business reason:** the runtime's honesty is its product. Freshness, drift,
  and mode must be legible at a glance or the transparency is theoretical.
- **Architecture refs:** ARCHITECTURE §2 (interfaces read the facade only),
  ADR-0001 (Textual), ADR-0012 (WOLF naming), `specs/design/tui-direction.html`.
- **Inputs → Outputs:** `runtime.dashboard()` / `runtime.diagnostics()` →
  rendered screens.
- **Allowed paths:** `src/tradeos/tui/**`, `src/tradeos/runtime/{views,journal,
  diagnostics}.py`, facade query methods, `tests/unit/test_tui*.py`.
- **Forbidden paths:** risk, brokers, providers, storage internals.
- **Acceptance criteria:**
  - Every number shown is computed in `runtime/` and tested there, not in a widget.
  - Drift gauge scales to the strategy's rebalance threshold. Off-scale is marked
    (◀ / ▶), never silently clamped.
  - Cash renders against its **floor**, never as drift (`min_cash_pct` is a
    constraint, not a target).
  - A failing doctor check halts the boot cascade in place with its fix hint.
  - `--calm` disables animation while every screen still renders complete content.
- **Non-goals:** per-symbol price sparklines (no price history is stored. Showing
  one would be fabricated data).
- **Tests required:** glyph unit tests incl. edge cases. Pilot tests per screen.
  Interface-discipline import test.
- **Safety class:** S0 (display only. No execution authority).
- **Rollback:** revert `tui/`. `TradeOSApp` alias keeps the old entry point name.
- **Completion evidence:** `scripts/verify.sh` green. 200 tests.

## T-032. Cycle + verdict screens ☑ done 2026-08-05

- **Objective:** make a decision watchable as it happens (pipeline tracker) and
  auditable after (thesis → full rule wall → execution receipt).
- **Business reason:** the architecture's central claim is that the model is one
  box between deterministic walls. The cycle screen shows that claim being true.
- **Architecture refs:** ARCHITECTURE §3, ADR-0008, ADR-0011.
- **Allowed paths:** `src/tradeos/tui/screens/{cycle,verdict}.py`,
  `src/tradeos/runtime/progress.py`, `runtime/cycle.py` (observer hook only).
- **Acceptance criteria:**
  - The progress observer is display-only: exceptions are swallowed and it
    cannot alter, delay, or abort a decision (`runtime/progress.py::emit`).
  - Progress is **not** recorded as events. The log stays the single audit source.
  - The verdict screen lists **every** rule result, including passed and advisory
    ones. A veto stops the cascade on the red ✗.
  - The rule count is explained (configured rules + per-proposal idempotency
    check), so "21/21" and "20 armed" cannot read as a contradiction.
  - Slippage is shown as a cost on both sides of a trade, never signed.
- **Non-goals:** approval mode keys (`a`/`r`): v0.2, when a mode above PAPER exists.
- **Safety class:** S1 (touches the cycle orchestrator. Observer is inert).
- **Completion evidence:** cycle/verdict Pilot tests. `test_no_bypass` unaffected.

## T-033. Journal + kill switch takeover ☑ done 2026-08-05

- **Objective:** a decision history where vetoes and no-actions carry the same
  weight as fills, and a kill screen that is deliberately the loudest thing in
  the app.
- **Business reason:** "we did not trade" is a result. Safety should not be tasteful.
- **Architecture refs:** RISK_POLICY_SPEC §5, ADR-0005 (event sourcing).
- **Allowed paths:** `src/tradeos/tui/screens/{journal,kill}.py`,
  `src/tradeos/runtime/journal.py`.
- **Acceptance criteria:**
  - The journal reducer is pure (events in, records out. No I/O, no clock reads)
    and therefore replayable.
  - Fills attach to their cycle even though order events correlate by proposal id.
  - Disengaging the kill switch requires two deliberate presses or the typed
    `wolf unkill`. One keystroke can never re-arm execution.
  - The kill screen names who engaged it, when, and why, read back from the log.
- **Non-goals:** day replay at 20× (needs T-027's replay harness wired to the UI).
- **Safety class:** S1 (kill-switch interaction. Engage/disengage still go through
  the facade and remain event-backed).
- **Completion evidence:** journal reducer unit tests. Kill-screen Pilot tests
  incl. the two-press invariant.
